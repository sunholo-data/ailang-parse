Parse a document archive at scale

Years of Word, PowerPoint and Excel files turned into structured JSON and Markdown your search or RAG system can use. It runs on your own machines, with no AI calls and no GPU, and nothing leaves your network.

Measured on 16 November 2026 with AILANG Parse 0.57.1 on one Apple M4 Max (16 cores) running 12 processes at once, over a mix shaped like an office archive: memos, reports, long documents with tables and pictures, slide decks and spreadsheets, 695 KB on average. Every file produced a JSON and a Markdown output.

Each output keeps what makes old documents worth searching: headings and section structure, tables with merged cells, lists, comments and tracked changes, speaker notes and sheet names. That structure is what lets a RAG system cite the right section instead of a page of flattened text; the benchmarks score it file by file against other parsers.

How long for yours

Time follows the number of documents, not the terabytes. Most of an office archive's bytes are pictures inside documents, and those are not decoded unless you ask for descriptions: a 2 MB slide deck full of photos parses about as fast as a short memo. So the first number to find is how many files you have, and how big they are on average.

A real archive is rarely all Office files. Video, photos, design files and backups often take most of the space and have no text to extract, and old archives hold many copies of the same file. Counting by type first, and skipping exact copies, usually shrinks the job a lot.

Run it

1. See what is in there. Count files by type before parsing anything:

find /archive -type f | sed -E 's/.*\.([^./]+)$/\1/' | tr 'A-Z' 'a-z' \
  | sort | uniq -c | sort -rn | head -20

2. One machine, one command. -r takes in every subfolder, and the output folder mirrors the archive, so Clients/Acme/2019/Proposal.docx becomes parsed/Clients/Acme/2019/Proposal.docx.json and .md. Files with the same name in different folders never overwrite each other.

docparse -r /archive --output-dir /parsed

3. Every core. One docparse process uses about one core. Split the file list across processes; DOCPARSE_INPUT_ROOT keeps every slice in the same mirrored layout. Outputs are written as each file finishes, so an interrupted run loses nothing already done.

export DOCPARSE_INPUT_ROOT=/archive
find /archive -type f \( -iname '*.docx' -o -iname '*.pptx' -o -iname '*.xlsx' \
     -o -iname '*.odt' -o -iname '*.odp' -o -iname '*.ods' -o -iname '*.eml' \) -print0 \
  | xargs -0 -n 1000 -P 12 docparse --output-dir /parsed

Set -P to the number of performance cores. Each process needs about 670 MB.

4. Skip exact copies (optional). Hash every file and keep the first path for each hash, then feed that list to step 3 instead of find:

find /archive -type f \( -iname '*.docx' -o -iname '*.pptx' -o -iname '*.xlsx' \) -print0 \
  | xargs -0 shasum -a 256 | sort -k1,1 -s | awk '!seen[$1]++' \
  | cut -c67- > unique.txt          # sha256sum on Linux

tr '\n' '\0' < unique.txt | xargs -0 -n 1000 -P 12 docparse --output-dir /parsed

5. Load it. The Markdown is ready for embedding as it is. The JSON gives typed blocks (headings, tables, lists, notes) for chunking that never cuts a table off its heading.

What takes longer

  • Big spreadsheets. Time grows with the number of cells: a workbook of three 1,500-row sheets took about 1.5 s on one core, and in the measured mix the spreadsheets took more time than all the Word and PowerPoint files together. Workbooks over 250,000 cells are refused with WORKBOOK_TOO_COMPLEX; split them by sheet.
  • PDFs with a text layer are read with pdftotext, which is quick but was not part of this measurement. Scanned PDFs need OCR, which is where large archives get slow and expensive; see PDF parsing for the local and AI backends.
  • Images and --describe (descriptions of pictures inside documents) call an AI model, a few seconds and a fee per image. Leave them off for the first pass.
  • Email (EML and MBOX) is supported; it was not part of this measurement.

Measure it yourself

The corpus generator and the runner are in the repository. The corpus uses invented text and random images, so it can be shared and rebuilt exactly; run it on your own hardware, or point the commands above at a sample of your archive.

git clone https://github.com/sunholo-data/ailang-parse && cd ailang-parse
pip install python-docx python-pptx openpyxl Pillow
bash benchmarks/throughput/run.sh 1 8 12 16     # process counts to try

Results are written to benchmarks/throughput/results/latest.json; the numbers on this page come from that file.

Frequently Asked Questions

Do our documents leave our network?

No. The command-line tool reads files from your disks and writes JSON and Markdown next to them. Word, PowerPoint and Excel files are parsed without any AI model or network call, so nothing is sent anywhere.

Does parsing an archive need a GPU or an AI model?

Not for Office files. DOCX, PPTX, XLSX and the OpenDocument formats are read directly from the file's XML, on ordinary CPUs. AI is only used if you ask for image descriptions or send scanned pages to the AI PDF backend.

Why does the size in terabytes say little about how long it takes?

Most of the bytes in an office archive are pictures inside documents. They are not decoded unless you ask for descriptions, so a slide deck full of photos parses about as quickly as a short memo. Time follows the number of documents and the amount of text and table data in them.

How do I find the original file for a parsed output?

With -r, or with DOCPARSE_INPUT_ROOT set, the output folder mirrors the archive: Clients/Acme/2019/Proposal.docx becomes Clients/Acme/2019/Proposal.docx.json and .md under the output folder. Two files with the same name in different folders never overwrite each other.

Can we use the hosted API for a backfill?

The hosted API is built for a steady stream of documents, and every plan has a daily request limit. For an archive of millions of files, run the command-line tool or the container on your own machines, or contact Sunholo about a managed run.
