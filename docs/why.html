The Invisible Assumption

Most business documents start as Office files: DOCX, PPTX, XLSX. Yet the usual approach is to export to PDF, then parse. That throws away structured data, then spends compute trying to recover it.

It's like taking a photograph of a spreadsheet and then using computer vision to read the numbers — when you could just open the file.

A DOCX file is a ZIP archive of structured XML, defined by the ECMA-376 standard. Track changes carry an author and a timestamp. Tables say which cells are merged. Comments are threaded. Each section has its own headers and footers. All of this is right there in the XML.

What Gets Lost

FeatureDirect XML ParsingAfter PDF Conversion
Track changes Author, date and change type kept Lost. You get the accepted or the rejected view only
Merged cells Exact colspan/rowspan, read from the XML Flattened, or guessed wrongly from the layout
Comments Author, thread and the text each comment is attached to Dropped
Headers / footers Kept per section, with first, even and odd pages separate Mixed into body text or ignored
Text boxes Position, content and stacking order kept Lost or garbled
Metadata Title, author, dates, keywords, revision count Stripped or only partly kept
Footnotes Numbered and linked to where they are cited Detached from the text they belong to
Hyperlinks Link text together with its URL Blue text only. The URL is lost
Legal, compliance and audit teams rely on every row in this table. Track changes in a contract are the negotiation history. Losing them is losing data, not a small drop in quality.

Why Parsers Use PDF

The OOXML specification is over 5,000 pages. Track changes alone span several XML namespaces, with moves and ranges that cross paragraph boundaries. Merged cells in DOCX tables do not work like HTML colspan: they use vMerge and gridSpan attributes that point to a separate grid definition. Numbered lists are worked out through several layers of numbering definitions and style overrides.

Writing a correct parser from scratch is a very large job. The cheaper choice was to convert to PDF, which LibreOffice already does, and parse the PDF, which has mature tools. Losing the structure was the price.

What changed

AILANG made it practical. AI agents write the parsing code from the ECMA-376 spec, and Z3 formal verification catches edge cases that manual testing would miss. The result: 63 verified contracts across 31 modules.

Frequently Asked Questions

Why does converting DOCX to PDF lose data?

A DOCX is structured XML. Converting it to PDF keeps only how the page looks, so track changes, merged-cell information and comments are lost. AILANG Parse reads the XML directly.

How should I parse Office documents for a RAG pipeline?

AILANG Parse returns typed blocks that keep heading levels, table structure and metadata. That gives cleaner chunks than flat text.

Is DOCX or PDF better for AI ingestion?

DOCX is better when the source was written in Word or Google Docs. AILANG Parse reads the DOCX XML directly, with no AI calls and no per-page billing. PDF conversion pipelines run OCR on every page and lose structure such as merged cells, track changes and comments.

What problems does PDF conversion cause for LLM document processing?

PDF conversion flattens tables, drops track changes and makes reading order unreliable. AILANG Parse avoids all three by reading the Office XML directly.

What is structural document extraction?

It means keeping a document's structure (headings, table cells, merged cells, tracked changes), not just its text. AILANG Parse returns typed blocks, so a heading, a table and a tracked change each come back as their own kind of element.
